# 北斗客户端需求共创

## 从实际使用者出发

本项目主要供 AI 通过 CLI 和 Lua 操作客户端。维护者提供现象、方向和取舍；助手应当说明谁遇到了什么问题、希望看见什么结果及其价值。普通实现选择由助手处理；只问会改变范围、验收或授权的问题。想法偏离项目定位或代价与价值不相称时，说明依据并给出替代方案。

先从技能所在的项目找到[开发约定](../../../AGENTS.md)和[项目入口](../../../README.md)，按需核对源码、文档和真实样本。区分已验证事实、已有但未经验证的入口和设想。文档没提到某项能力，不足以证明它缺失。草稿或导出的正文放在主检出的 `tmp/<任务标识>/`；原始私密证据留在所属环境。

## 判断是否建单

- **Feature**：新增或恢复一项使用者需要的能力。用[用户故事模板](../../../.github/ISSUE_TEMPLATE/user-story.md)写明消费者、场景、结果、价值和至少一项可观察的验收标准。
- **Bug**：当前版本已观察到的行为与有依据的预期不符。用[缺陷模板](../../../.github/ISSUE_TEMPLATE/bug.md)记录版本、条件、预期、实测结果和复验方式。根因可以未知；仅缺样本或尚未复现的猜想留在讨论中，需要专门核验时交回维护者规划。
- 按独立用户结果查重，覆盖开放和已关闭的 Issue。已有开放单能承载的就更新；历史交付要核对当前版本，不把旧单勾选当作当前能力证明。选择[一个领域标签](../../../docs/ISSUE_LABELS.md#领域标签)，不用标签表示进度。
- 需求讨论中达到上述条件即可按对应原生类型建单或更新，返回链接、验收结果的判据及待确认项。用户只要求讨论或草拟时不发布。技术问答、无明确使用价值的方案比较留在会话中。

涉及玩法时写明后端、分区、角色条件和客户端可核对的效果；开发服准备、离线测试和真实游戏效果分别记录。脚本输入或并发策略的歧义可参考[讨论案例](references/discussion-cases.md)。

建单不自动开工。一次可独立交付的 Feature 或 Bug 就是执行单；维护者可直接指定原单，不必先拆 Task。需要讨论多项独立交付时，再按[规划技能](../beidou-pilot-issue-planning/SKILL.md)拆分并汇总。
