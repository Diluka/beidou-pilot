# 伴游机器人：设计与实施路线

- 状态：设计草案，未改产品代码
- 日期：2026-11-20
- 适用：北斗 V17 客户端；机器人跑 headless，玩家跑原版 GUI
- 目标读者：维护者、Lua 策略作者、后续接手的 AI 会话

## 0. 一句话结论

把机器人做成 **“常驻 Lua 运行时 + 可复用技能库 + 内容包 + 外部控制面”**，而不是“让大模型逐帧写脚本”。玩家私聊和大模型都只提交**意图**，角色动作的唯一控制者是常驻 Lua；没有大模型时，机器人仍按脚本和计划完整工作。

## 1. 当前瓶颈的诊断

这个项目底层能力已经很多：双端客户端、tick Lua、原生观察、静态地形导航数据、GUI 对话/商店、AP/SP、通知气泡、世界门户路线。真正缺的不是又一个底层命令，而是把已有能力组装成“能连续陪玩”的那一层。

具体缺口：

1. **没有常驻运行时。** 现有策略多是一次性脚本：有界目标、结束后角色静止、没有跨会话状态、没有命令入口、没有恢复策略。机器人需要连续几小时工作，能暂停、恢复、换模式、崩溃后回来。
2. **社交面缺失。** tick Lua 没有聊天收发、队伍观察/入队、NPC 交互、交易动作；`game.chat` 两端 unsupported，队伍成员/队员 HP/队友地图没有领域，headless 的 `Interaction::Activate` 有实现但没有调用者。没有这些，“组队、跟随、组队任务、BOSS”无法闭环。
3. **大模型放错了位置。** 已退役的 Codex harness 让模型在控制回路里逐轮写 Lua、调 CLI。它慢、贵、脆，而且模型一停机器人就停。正确位置是“慢速参谋”：读状态、改计划、回答自然语言，不参与逐帧动作。
4. **没有端到端验收。** 现有验收多是“某个动作/观察在某个场景成立”，没有“玩家和机器人一起玩 30 分钟”的结果。没有这条线，底层能力会继续增长，机器人仍然不存在。
5. **路径和跨图能力被高估。** `context.route` 在普通 `script run/start` 中实际没有注入；运行时不能查询路线。同图跟随可做，跨图跟随/自主旅行需要小改 CLI 或原生路线查询。先把同图做扎实。

结论：**停止继续铺底层能力，先做一条垂直切片**：一个 headless 机器人，跟随玩家、打怪、喝药、拾取、能收指令、能恢复，连续跑 30 分钟。之后再加聊天、组队、组队任务、BOSS 和大模型。

## 2. 目标与非目标

### 2.1 目标

- 玩家在 GUI 正常游玩；机器人在同服 headless 客户端上以角色身份陪伴。
- 机器人能：跟随玩家、协助战斗、拾取、喝药、复活、在安全点等待、按命令切换模式。
- 玩家能通过私聊控制机器人；没有大模型时用固定命令，接入大模型后可用自然语言。
- 机器人能和玩家组队，完成至少一个经典组队任务；能和玩家一起打至少一个 BOSS。经典组队任务默认 3 人起，必要时用第二个机器人补位（玩家 + 2 机器人）。
- 大模型可参与行为决策（选目标/换模式/处理异常）和角色养成（计划、验证、执行），但不是运行必需。
- 机器人能连续运行，崩溃/断线后由宿主侧监督恢复；有状态、事件和可核对的结果。
- 每一步都有可观察的验收，不依赖“看起来能跑”。

### 2.2 非目标（第一阶段不做）

- 不做服务端修改，不读写正式数据库。
- 不做全自动主线/转职/交易市场/PVP。
- 不做 GUI 机器人；机器人固定 headless，玩家用 GUI。GUI 专属的换装、商店、部分对话通过“维护窗口”交给人或外部 CLI。
- 不做帧级完美战斗、闪避、连招或全职业精通。
- 不做通用多智能体框架；多机器人用清单 + 协调器，不引入消息中间件。
- 不做新的宏 DSL/JSON 动作预设；行为是 Lua 代码，指令是固定小词表。
- 不复活旧 Codex harness 的控制方式。

### 2.3 假设

- 机器人角色是专用账号/角色，等级、装备、药品满足目标内容；玩家角色和机器人同服同频道。
- 机器人使用正常客户端动作；操作者自行确认服务器规则允许自动化。
- 机器人固定 headless（第一阶段）；需要 GUI 专属操作时单独开维护窗口，不与常驻脚本并发。
- 玩家是机器人 owner；owner 的私聊/队伍消息是可信指令来源，其他玩家默认不可指挥机器人。
- 经典组队任务默认 3 人起；第一阶段的组队任务验收以“玩家 + 2 个机器人”为目标，玩家 + 1 个机器人只覆盖 1～6 人 BOSS/野外内容，不把改服务器人数配置当成默认路径。

### 2.4 后端分工与差异处理

- 机器人固定 headless。开发任务只实现和验收 headless；任务正文锁定预期行为。
- GUI 行为是权威参考，但差异核对由独立的“后端差异审计”任务在专门会话中完成，产出差异报告或临时补充任务；不把差异排查塞进功能任务，也不因等待 GUI 对比延长当前交付。
- 如果某个 headless 行为还没有可靠依据，先派发前置调查/取证任务，把预期行为写成可复核的契约；功能任务只消费已锁定的证据，不自行选后端或改验收标准。
- 差异审计任务的最小内容：同一角色/场景/版本分别在 headless 与 GUI 执行同一输入，记录两边可观察到的行为、时间和证据；只报告差异与影响，不顺手改代码。差异影响当前功能时另开定向修复任务；不影响时只记录。
- 差异审计的样本、场景、版本和原始证据留在所属环境；公开记录只写不影响当前任务交付的结论。

### 2.5 GUI 兼容选型

- GUI 兼容优先通过客户端钩子/桥的直接指令实现；模拟键鼠只在有证据表明钩子不可用时使用。
- 选型由维护者决定，开发任务不得自行切换实现方式。证据不足时先派发钩子/协议调查任务，再排对应开发任务。
- 调查任务至少给出：钩子/桥的入口与调用方式、可观察的返回/错误、适用客户端版本、最小调用示例、失败时的回退证据。没有这些证据不排 GUI 兼容开发任务。

## 3. 设计原则

1. **单控制者。** 同一角色同一时刻只有一个 tick 会话拥有动作输入。玩家、LLM、CLI 都只发意图，不直接按键、不另起控制会话。
2. **快慢分离。** 30Hz Lua 负责反射、移动、战斗、自保；秒级到分钟级的大模型负责目标、计划、社交、养成。LLM 不在 tick 回路里。
3. **脚本优先，LLM 可选。** 没有 LLM 时，已知命令 + 计划文件就能完整工作；LLM 只是增强。
4. **观察即事实。** 动作受理不等于命中/拾取/恢复；以本端观察和可核对结果推进，未知保持未知。
5. **有界可退。** 每个模式有进入条件、退出条件、超时、安全点；不可逆动作（洗点/转职/大额交易）必须显式计划 + 人确认。
6. **内容与引擎分离。** 导航、战斗、跟随、社交是引擎；地图、组队任务、BOSS 是内容包。加内容不改引擎。
7. **离线可测。** 导航图、指令解析、模式状态机、组队任务阶段机用纯 Lua 场景测试；真实游戏效果单独验收。
8. **人机同协议。** 玩家私聊和大模型都走同一套指令/意图；LLM 只是另一个有白名单的指令来源。
9. **一角色一实例。** 一个机器人一个账号角色一个客户端；多机器人靠宿主侧的编队清单和协调器，不共享客户端。
10. **不造新语言。** 行为是 Lua 函数；内容是 Lua 表；指令是 10～15 个动词；LLM 输出结构化意图，不输出可执行代码。

### 4.1 组件职责

| 组件 | 职责 | 不负责 |
| --- | --- | --- |
| 玩家 GUI | 正常游玩、带队、发起组队/对话、发指令 | 机器人内部状态 |
| Bot Runtime（Lua） | 唯一控制者；观察、模式、导航、战斗、跟随、社交、状态发布 | 跨进程调度、模型调用 |
| 内容包（Lua） | 地图路线、组队任务阶段、BOSS 策略参数 | 引擎实现 |
| botctl（宿主） | 启动/停止客户端、启动/监督脚本、读取状态、发送指令 | 逐帧动作 |
| LLM 代理（可选） | 读状态/事件、改计划、自然语言回复、发起养成 | 直接按键、绕过机器人 |
| 原生客户端能力 | 聊天、队伍、交互、路线等新域/动作 | 策略 |

### 4.2 部署形态

- 每个机器人角色一个 `headless` 工作台实例，一个常驻 tick 会话。
- 机器人代码是目录脚本包，装到该角色 `/work/scripts/bot/`；状态写在 `/work/bot/`。
- 宿主侧 `botctl` 通过现有 `workbenches/workbench` 启停客户端和脚本，不绕过生命周期锁。
- 玩家和机器人同服；玩家用 GUI 工作台，机器人用另一个角色工作台。
- LLM 代理跑在宿主，读 `/work/bot/` 的镜像目录（宿主路径 `private/workbenches/.../bot/`），不进入游戏容器执行任意命令。

## 5. Bot Runtime

### 5.1 目录与装载

机器人是 tick 目录脚本包：

```text
/work/scripts/bot/
  main.lua              -- 入口：装配、tick 管线、返回 done
  defaults.lua          -- 默认参数（owner、阈值、技能、物品、安全点）；角色覆盖放 /work/bot/config.conf
  lib/
    io.lua              -- 状态/事件/邮箱/原子写/日志轮转
    terrain.lua         -- 消费 navigation 的平台图、A*、平台定位
    move.lua            -- 逐边执行：走/小步/跳上/落下/绳/门户
    follow.lua          -- 动态跟随
    combat.lua          -- 选怪、接近、面向、攻击/技能、命中核对
    sustain.lua         -- 喝药、死亡/复活、无药撤退
    loot.lua            -- 拾取
    social.lua          -- 聊天/队伍（原生能力就绪后）
    state.lua           -- 模式、黑板、检查点
  content/
    hunt.lua            -- 狩猎点/怪物/等级段
    pq/henesys.lua      -- 第一个组队任务
    pq/kerning.lua      -- 后续
    boss/field.lua      -- 野外 BOSS
    boss/bossrush.lua   -- 后续
```

- 入口只做装配，不写具体策略。
- 模块用 `require("lib.terrain")` 这种包内相对名；不写死 `/work` 或 `Z:\work`。
- 代码同步到角色目录；状态在 `/work/bot/`，不随代码同步覆盖。
- 代码版本写进 `state.json`，方便核对本次运行到底跑了哪版。

### 5.2 tick 管线

每个 tick 固定顺序，前一层可以短路：

```text
main(context):
  1. io.poll_commands    -- 每 0.5s 读一次文件邮箱；私聊指令在社交能力就绪后并入
  2. safety              -- 死亡、低血、无药、超时；可短路
  3. decide              -- 模式/子状态/目标选择；只写黑板，不做动作
  4. move                -- 执行当前路径/边；可短路
  5. combat              -- 接近/面向/攻击/技能；可短路
  6. loot                -- 安全时拾取
  7. publish             -- 每 1s 写 state.json / events.jsonl
```

- `safety` 必须最先；低血/死亡不能被跟随或战斗覆盖。
- `decide` 不直接写 `player`，动作由 `move`/`combat`/`sustain` 执行，保证动作槽只有一个写者。
- `publish` 只做投影，不参与决策。
- 每个 tick 的路径复用：目标平台/路径只在目标变化或场景代次变化时重算；不要每帧跑 A*。
- 默认 30Hz、100ms；文件轮询和状态发布放到低频计数（如每 15 tick），避免每帧 I/O。

### 5.3 世界模型

只从本端只读领域构建，不猜测：

| 字段 | 来源 | 用途 |
| --- | --- | --- |
| `character` | `game.character` | HP/MP/位置/等级/经验/动作忙闲 |
| `map_id`、`scene_generation` | `game.world` / `context.scene` | 换图/重规划 |
| `terrain` | `context.scene.terrain.navigation` | 平台图/A* |
| `owner` | `game.scene.players` 按 owner 名字/ID 匹配 | 跟随 |
| `mobs` | `game.scene.monsters` | 选怪/验证命中 |
| `drops` | `game.scene.drops` | 拾取 |
| `party` | 新 `game.party`（待原生） | 队伍/队员 |
| `chat` | 新 `game.chat`（待原生） | 指令 |
| `inventory`/`quests` | 既有领域 | 药品/任务/物品核对 |

- owner 不在同图时 `owner.present=false`，不拿别的玩家代替。
- 玩家位置来自 `scene.players` 的逐帧采样，可能为空；为空时等待，不推断。
- 怪物 HP% 只有 headless 有；用它验证攻击进展，GUI 不适用（机器人不用 GUI）。
- 未知字段保持 `nil`，不用 0 或空表填充。

### 5.4 模式与状态机

| 模式 | 进入 | 行为 | 退出 |
| --- | --- | --- | --- |
| `recover` | 启动/重启/异常后 | 观察、喝药、走到安全点、确认身份 | 安全且有计划 |
| `idle` | 无指令/停止 | 在安全点等待，定时发布状态 | 收到指令 |
| `follow` | `!follow` | 跟随 owner，保持距离，必要时协助 | `!stay`/`!hunt`/危险 |
| `assist` | `!assist` | 跟随 owner，攻击 owner 附近目标 | `!follow`/`!stop` |
| `hunt` | `!hunt`/计划 | 在狩猎点选怪、打怪、拾取、巡逻 | `!follow`/`!stop`/升级阈值 |
| `travel` | `!go MAP` | 按注入路线跨图（需先补路线注入/查询，后续） | 到达/失败 |
| `pq` | `!pq` | 内容包阶段机，跟随/防守/收集 | 通关/失败/`!stop` |
| `boss` | `!boss` | 跟随 owner 到 BOSS，输出/喝药/复活/拾取 | 击杀/失败/`!stop` |
| `maintain` | 升级/SP/补给阈值 | 回安全点、停手、写 handover、返回 `done` | 外部重启 |
| `dead` | HP=0 | 复活一次、等待、报告 | HP>0 |

- 模式切换必须记事件（从哪到哪、原因、指令 id）。
- `maintain` 是唯一主动结束会话的正常路径；它保证角色已停手、输入已释放、状态已写盘。监督器看到 `maintain` 后不得自动重启，必须等 handover 的外部步骤完成并更新计划后再拉起。
- 任何模式都有超时/最大尝试；超过就回 `recover` 或 `idle` 并报告。

### 5.5 指令与优先级

指令来源：owner 私聊、owner 队伍消息、宿主邮箱（LLM/CLI）。优先级：

```text
安全/死亡处理 > owner 直接指令 > LLM 意图 > 计划默认 > 空闲
```

- owner 直接指令永远压过 LLM；LLM 不能取消 owner 刚下的命令。
- LLM 意图带 TTL（如 120s），过期作废；owner 指令可带 TTL，也可持续到被替换。
- 同一 id 幂等；重复投递只执行一次。
- 未知指令拒绝并回执；不猜测。
- 非 owner 的消息只记录，不执行；可配置一句礼貌拒绝。

指令词表（第一版）：

```text
!follow [名字]     跟随（默认 owner）
!stay              停在原地
!come              走到 owner 身边（同图）
!assist [on|off]   跟随并协助攻击 owner 附近目标
!hunt [地图]       在当前狩猎点打怪；指定地图需要先有跨图路线（后续）
!pq [名字]         进入指定组队任务模式
!boss [名字]       进入指定 BOSS 模式
!pot hp=60 mp=30   设置喝药阈值
!loot on|off       拾取开关
!stage N           手动校正组队任务阶段
!status            回报模式/地图/HP/目标/队伍
!stop              停手、停在原地
!help              指令列表
```

- 私聊带 `!` 的走指令；不带 `!` 的自然语言在有 LLM 时转给代理，没有则回“我只听得懂 ! 指令”。
- 队伍消息默认只接受 owner 的 `!` 指令；其他队员的消息只记录。
- 回复优先私聊 owner；队伍协调可用队伍消息（后续）。

### 5.6 状态、事件、检查点

`/work/bot/` 下的文件是机器人和宿主/LLM 的唯一接口：

| 文件 | 写者 | 内容 |
| --- | --- | --- |
| `state.json` | 机器人，1s 原子写 | 模式、地图、坐标、HP/MP、owner、目标、队伍、最后指令、错误、版本、会话 id |
| `events.jsonl` | 机器人，追加 | 指令、模式切换、聊天、队伍、升级、死亡、卡住、组队任务阶段、BOSS、错误 |
| `queue/*.cmd` | 宿主/LLM/CLI | 意图：`id/kind/target/args/ttl/source` |
| `queue/done/`、`queue/rejected/` | 机器人 | 回执：ok/拒绝原因 |
| `plan.conf` | 人/LLM | 常驻计划：owner、默认模式、狩猎地图、阈值、养成目标 |
| `config.conf` | 人 | 本角色配置：技能 ID、药品 ID、安全点、白名单 |
| `checkpoint.conf` | 机器人，低频 | 高层状态：模式、目标地图、组队任务阶段、计划版本 |
| `handover.json` | 机器人 | 进入维护：原因、当前状态、需要外部做的步骤 |

- 写入用 `临时文件 + rename`；读方容忍短暂缺失/半文件，失败重试。
- 事件日志按大小轮转（如 1 MiB → `events.1.jsonl`），避免无限增长。
- `state.json` 只放投影，不作为机器人恢复的唯一依据；恢复以现场观察 + `checkpoint.conf` + `plan.conf` 为准。
- 不把账号、密码、私密配置写进状态/事件。

### 5.7 安全与恢复

| 条件 | 动作 | 通知 |
| --- | --- | --- |
| HP < 喝药阈值 | 喝对应药；保持到阈值以上 | 无药时通知 |
| HP < 危险阈值 | 撤退到 owner/安全点；停止狩猎 | 是 |
| MP < 阈值且需要技能 | 喝 MP 药；否则普攻 | 可选 |
| 药品耗尽 | 停止狩猎，跟随/等待 | 是 |
| 死亡 | `player.revive()` 一次；等待 HP>0 | 是 |
| owner 消失 < 60s | 原地等待/在安全点等 | 30s 一次 |
| owner 消失 > 5min | 回城/安全点，进入 idle | 是 |
| 卡住 2s | 跳/换边/重规划 | 5 次后 |
| 路径失败 3 次 | 禁用该边、重规划 | 是 |
| 场景代次变化 | 清旧路径，按新地形重规划 | 事件 |
| 队伍解散 | 切回跟随 owner | 是 |
| 未知地图/无路线 | 停手，等待指令 | 是 |
| 指令非法/过期 | 拒绝/忽略，回执 | 可选 |

- 所有“回城/传送”动作只在有路线/已知安全点时执行；没有就停在原地，不猜。
- 复活只提交一次；结果不明先观察 HP/地图，不重发。
- 维护/养成动作不在机器人里做；机器人只负责停手、写 handover、退出。

### 5.8 性能与长期运行

已核实事实：

- 默认 30Hz / 100ms / abort；预算 hook 每 1000 条 VM 指令检查墙钟，阻塞 C 调用不可抢占。
- `context.state` 无上限；`TickRuntime` 的 sessions 不会清理，反复启动会累积；`script-events.jsonl` 无限增长。
- headless 断线进程退出，没有自动重连。

对应设计：

- 机器人是一个长会话，不频繁重启；监督器只在会话结束/客户端退出时拉起。
- 状态/事件/邮箱放在低频路径（每 0.5～1s），不占每帧预算。
- 不在 tick 里做 JSON 解析大文件；指令是行式 key=value，状态只写不读。
- 定期（如每天，在 idle/维护窗口）由监督器安排一次正常关闭/重开，清掉会话累积；重开前写 checkpoint，避免打断玩家正在进行的组队任务。
- 事件日志轮转；`game.log` 只用于关键节点，不逐帧。
- 战斗/寻路使用缓存；A* 只在目标/场景变化时跑。

## 6. 核心技能

### 6.1 导航

- 平台图/A* 直接消费 `context.scene.terrain.navigation` 已派生的 `platforms/walls/ropes/candidates`；走/小步/跳上/落下/绳边的执行相位参考已验证的 tick-walk。参考脚本保存在主检出 `private/workbenches/live/workspace-warrior/runtime/.../scripts/*.lua` 的运行快照中（带嵌入 context 的旧格式），落地时只抽执行相位并改到当前 `context.game` 契约，不直接提交整文件；不要重新从 footholds 做墙切分/平台合并。
- 已有事实：跳跃高度约 78px、地面速度约 130px/s、跳跃水平惯性约 58px；规划用保守值（跳高 75、落点 4～65、抓绳 95）。
- `terrain_platform_at(x,y,tolerance)` 定位 owner/自己/怪物所在平台；目标在另一平台时 A*。
- 路径只在目标平台变化、场景代次变化、卡住重规划时重算；同平台直接 `walk_to`。
- 每次边执行都有超时和失败计数；失败边按代次禁用；连续失败回 `recover`。
- 跨图不在第一版：`context.route` 当前没有注入，运行时也没有路线查询；先做同图，跨图后续补 CLI/原生。

### 6.2 跟随

- owner 从 `scene.players` 按名字/ID 匹配；名字可空，ID 优先。
- 同平台：距离 > 80px 朝 owner 走；< 40px 停；owner 移动时按 2～5Hz 重算。
- 不同平台：以 owner 的平台为目标，A* 到最近可达点；owner 在绳上时走到绳的 x，等待/跟随上下。
- owner 换图：第一版在最后可见的门户/安全点等待并通知；不做跨图追。
- owner 死亡：走到 owner 附近等待，不替 owner 复活。
- 跟随中 owner 被怪攻击：`assist` 开启时攻击 owner 附近目标；否则继续跟随。
- 绝不为了追 owner 跳下不可回的高台；宁可等待并报告。

### 6.3 战斗

- 目标选择：
  - `assist`：owner 周围 300px 内、离 owner 最近的活怪；没有则离自己 200px 内最近。
  - `hunt`：以狩猎点为圆心、leash 半径内最近活怪；没有则巡逻/等待刷新。
  - 避开等级过高/无法命中的怪；BOSS 只在 `boss` 模式选。
- 接近：目标在攻击距离外时走/跳到范围内；不追出 leash。
- 面向：用短促移动朝向目标；没有独立 face 动作，接受这一限制。
- 攻击：保持 `player.attack()` 或 `player.skill(id)`；用 `action_idle` 控制节奏；MP 不足切普攻。
- 命中核对：headless 用怪物 `hp_percent`/消失/经验变化；连续 N 次无进展则换位/换目标。
- 不抢非队友的怪；不引怪到 owner 身边；BOSS 技能/机制不在第一版。

### 6.4 补给与自保

- 药品 ID 从 `config.conf`；按 HP/MP 比例选择。
- `player.use_item` 是持续意图，达到阈值必须撤下；不能一次调用当一瓶。
- 无药/药量低于阈值：停止狩猎，跟随/回安全点，通知。
- 死亡：复活一次；等待；回安全点；等 owner/指令。
- 低级角色被高怪围：撤退，不硬打。

### 6.5 拾取

- 只拾取 150px 内、落地/可拾取的掉落；owner 在 100px 内时先等 0.5s，避免抢拾。
- `player.pickup()` 保持；用背包数量/掉落消失核对；失败重试一次。
- BOSS/组队任务阶段按内容包的拾取规则；不拾取任务关键物品以外的东西（可配置）。

### 6.6 社交（原生就绪后）

- 聊天：读私聊/队伍消息，按 owner 白名单过滤；回私聊/队伍；1 秒最多一条，长度限制。
- 队伍：接受 owner 的邀请；观察成员/队长/地图/HP；不主动踢人/换队长。
- 组队任务/BOSS 协调：owner 是队长；机器人跟随/防守/输出，不抢 NPC 对话。
- 交易（KPQ 需要）：后续；第一版不承诺。

### 6.7 交互（后续）

- 暴露 headless 已有的 `Interaction::Activate`：`player.interact(ref)` 一次性请求，ref 来自 `game.interaction.page.controls` 或 NPC 引用。
- 用途：机器人独立接任务、NPC 对话、商店、KPQ 的问答/交物品。
- 第一版不做；KPQ 依赖它。

## 8. 外部控制面与 LLM

### 8.1 文件协议

- 宿主路径：`private/workbenches/{live,dev}/NAME/bot/`；容器内 `/work/bot/`。
- 指令：`queue/<seq>-<id>.cmd`，内容 `key=value` 行；写入方先写 `.tmp` 再 rename 成 `.cmd`；机器人只读 `.cmd`，处理后移到 `done/`/`rejected/` 并写回执。
- 状态：`state.json`；事件：`events.jsonl`；计划：`plan.conf`；配置：`config.conf`；维护：`handover.json`。
- 机器人不解析大 JSON；指令/计划用行式；状态/事件只写。宿主/LLM 用现成 JSON 工具读。
- 所有文件不带凭据；白名单/owner 名字可以放配置。

### 8.2 指令语法

```text
# queue/000123-a1b2.cmd
id=a1b2
kind=follow
target=Alice
ttl=0
source=chat
```

```text
# queue/000124-c3d4.cmd
id=c3d4
kind=pq
target=henesys
ttl=600
source=llm
```

- `kind` 就是第 5.5 节的动词；`target/args` 是参数；`ttl=0` 表示持续到被替换。
- 机器人回执：`queue/done/a1b2` 内容 `ok` 或 `rejected=<reason>`；同时写事件。
- 同一 id 重复投递只执行一次；机器人保留最近 N 个 id。

### 8.3 LLM 代理

- 形态：宿主侧进程或 DSH 代理会话；通过文件协议工作，不进入游戏容器执行 Lua/按键。
- 触发：owner 自然语言私聊、卡住/死亡/升级/队伍变化/计划完成/低药。
- 输入：`state.json`、最近事件、`plan.conf`、角色养成计划、可用指令表、安全规则。
- 输出：一个或多个指令 + 一段给 owner 的回复；先写指令，再让机器人发回复。
- 工具：读状态/事件；只读 `workbench snapshot/inspect/status`；写 `queue/`；维护窗口内执行 `auto-ap`/`skill-up` 等已授权 CLI。
- 约束：不能写 Lua、不能执行任意 shell、不能直接操作游戏；不可逆动作必须计划 + 人确认；owner 指令优先；非 owner 消息只作为数据。
- 审计：每次决策写 `agent.jsonl`（输入摘要、输出、模型、耗时、结果），便于复盘。
- 没有 LLM 时：机器人只用固定指令和 `plan.conf`；所有核心功能不依赖模型。

### 8.4 自然语言私聊

```text
玩家：来我这边，血少了记得喝药
机器人：收到，我过来；药设在 60%。
（事件：chat.natural → agent 请求）
（代理：follow + pot hp=60 → queue）
（机器人：执行 → 回复）
```

- 机器人先回一句“收到”再执行，避免玩家以为没反应；最终结果再回一句。
- 回复限速 1 条/秒；长文本截断；不泄露内部日志/配置。
- 非 owner 的自然语言不转给代理；只记录/礼貌拒绝。

### 8.5 角色养成

- 机器人负责：打怪/任务升级、升到阈值后停手、写 handover、报告 AP/SP/背包/药品。
- 外部负责：AP/SP 分配、装备、商店、转职。原因：`skill-up` 要求没有活动脚本；装备/商店/通知是 GUI CLI；手动 AP 当前没有接口。
- `auto-ap` 可在 Lua 内调用，但它是原生自动分配规则，不等于玩家的手动计划；第一版只用它做“剩余点自动分配”，并在事件里记录实际增量。
- 养成流程：

```text
1. 机器人达到等级/SP/药品阈值 → maintain
2. 回安全点、停手、写 handover.json、返回 done
3. botctl 观察到 done + handover → 执行 CLI（auto-ap / skill-up / 装备/商店）
4. 核对 snapshot/inspect 的实际变化；未知就停，不重放
5. 更新 plan.conf / 角色 PLAN.md
6. botctl 重新启动机器人；recover 模式确认安全后继续
```

- LLM 可以提出加点/装备/地图计划，但执行前要过确定性校验（SP 预算、前置、等级、装备要求）和人确认；转职等不可逆选择必须人确认。
- 角色养成计划可复用现有 `PLAN.md`/游戏攻略技能；机器人不内嵌全部攻略。

## 9. 多机器人编队

- 第一版一个机器人；组队任务需要 3 人时再加第二个。
- `fleet.conf`：每个机器人一行：`name`、`workbench`、`role`、`owner`、`party`、`content`、`offset`。
- `botctl` 负责：按清单启停客户端/脚本、读各机器人状态、发指令、监督重启。
- 队伍形成：玩家创建队伍并邀请；机器人只接受 owner 邀请；不主动邀请/踢人。
- 角色分工：`follow`/`assist`/`defend`；同图跟随时用左右偏移避免叠在一起。
- 协调器：宿主侧脚本，按地图/阶段给每个机器人发 `!stage`/`!defend`/`!follow`；不共享 Lua 状态。
- 组队任务：玩家队长；机器人负责防守/输出/拾取；阶段以地图/事件/玩家指令校正。
- BOSS：玩家指挥；机器人跟位/输出/喝药/复活；不抢机制。
- 规模：先 2 个机器人（玩家 + 2 = 3 人）；资源/稳定性测过再扩。

## 10. 需要补的客户端能力

| 能力 | 为什么需要 | 后端 | 优先级 | 最小验收 |

| 队伍邀请接收/接受、成员列表 | 组队、跟随、队员状态 | headless | P0 | 玩家邀请机器人，机器人接受；观察成员/队长/地图 |
| 队员 HP/地图（可选） | 牧师/支援/找人 | headless | P1 | 队伍成员 HP 变化可读 |
| `player.interact(ref)` | NPC 对话/任务/商店/KPQ | headless | P1 | 打开 NPC 页面并选择一个控件，页面变化可核对 |
| 运行时路线查询/注入 | 跨图跟随/自主旅行 | CLI/Lua | P2 | 脚本运行中拿到 A→B 的腿序列 |

- 原生改动要遵守现有能力声明、领域来源、未知语义和 CLI/tick 文档同步规则。

## 12. 测试与验收

### 12.1 离线

- `terrain`：给定 `navigation` fixture，平台图/A* 的单元测试；同平台/跳上/落下/绳/墙切分/死路；真实地图 fixture 单独覆盖。
- `move`：用假状态机模拟边执行，验证相位/超时/失败。
- `follow`：owner 同平台/不同平台/消失/换图，验证目标/停距/等待。
- `combat`：目标选择/射程/MP/无进展换位。
- `command`：解析/优先级/TTL/幂等/owner 过滤。
- `pq`：Henesys 阶段机；地图变化/兔子死亡/超时。
- 运行：`lua`/`luajit` + 场景 fixture；不启动客户端。CI 可加一步 Lua 测试（现有 Python 测试之外）。

### 12.2 合同/双客户端

- 私聊：A 发 B 收；B 回 A 收；内容/发送者/频道正确。
- 队伍：A 邀请 B；B 接受；双方成员/队长/地图一致；B 离开。
- 队员 HP：受伤后 A 看到 B 的 HP 变化（如实现）。
- 交互：打开 NPC 页面、选择一个控件、页面变化/关闭（如实现）。
- 双客户端用开发服独立账号；不改常驻数据。

### 12.3 真实游戏

| 场景 | 通过条件 |
| --- | --- |
| 30 分钟跟随/打怪 | 跟随距离 < 120px 占 90%；无 >10s 卡住；无死亡；有经验/击杀增长 |
| 私聊指令 | `!follow`/`!stay`/`!status` 2s 内响应并改变行为 |
| 组队 | 玩家邀请后入队；跟随进图；协助攻击 |
| Henesys PQ | 玩家 + 2 机器人通关；兔子存活；机器人清怪/拾取；队长完成对话 |
| BOSS | 玩家 + 机器人击杀；机器人喝药/复活/拾取；不引怪害队友 |
| 自然语言 | 玩家一句话 → 代理 → 指令 → 行为/回复正确 |
| 养成 | 升级后停手；AP/SP 执行并核对；重启继续 |
| 24 小时 | 人为杀客户端/断网后监督器恢复；无重复会话/重复控制 |

### 12.4 指标

- 跟随距离均值/最大值、owner 丢失时长、卡住次数、死亡次数、喝药次数、击杀数、经验/小时、拾取数、指令延迟、LLM 延迟、重启次数、会话时长。
- 指标写事件/状态，验收时汇总；不记录私密数据。

## 13. 风险与对策

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| 原生聊天/队伍协议不一致 | P2/P3 失败 | 先读服务端源码/包结构；双客户端 spike；小步验收 |
| 路径在复杂地图失败 | 跟随/任务卡住 | 复用已验证 tick-walk；先做 1～2 张图；卡住恢复；手动兜底 |
| Henesys PQ 阶段/兔子机制理解错 | 任务失败 | 先在开发服复现；内容包按事件/地图校正；队长手动 `!stage` |
| KPQ 需要交互/交易 | 无法按“经典”完成 | 明确排到 P1 原生能力之后；先做 Henesys；不虚假验收 |
| LLM 幻觉/越权 | 乱加点/乱跑 | 指令白名单/TTL/优先级；不可逆动作人确认；审计 |
| 长期运行会话/日志累积 | 内存/磁盘增长 | 单长会话；事件轮转；每日正常重启；后续修 Runtime 清理 |
| 多机器人资源/冲突 | 卡顿/抢怪 | headless；先 2 个；错位/分工；资源监控 |
| 服务器规则/封禁 | 账号风险 | 正常客户端动作；限速；操作者确认规则；不做异常包 |
| 维护窗口与常驻脚本冲突 | 加点/换装失败 | `maintain` 停手→写 handover→退出→CLI→重启 |
| 无手动 AP/装备接口 | 养成不完整 | 第一版 auto-ap + 人/GUI 维护；后续补接口 |
