# 客户端能力边界

本页说明客户端当前能做什么、哪些入口仍缺失，以及这些边界对脚本和伴游机器人的影响。具体命令、字段和错误以 [CLI](CLI.md)、[Tick Lua API](LUA_TICK_API.md)、[控制协议](CONTROL.md) 和当前 `capabilities` 为准；本页不替代接口文档。

项目当前定位是**可核验的游戏客户端自动化工具**：操作者通过 CLI 观察、提交 tick Lua、核对游戏结果。伴游机器人是建立在这套工具之上的应用层，仍在设计与分阶段实施中，见 [伴游机器人设计与路线](COMPANION_BOT.md)。边界会随交付变化；未知和未支持保持明确，不用另一后端补齐。

## 动作与控制

- **角色动作只从 tick Lua 提交。** 移动、跳跃、普攻、技能、拾取、用药都通过 `context.game.player` 的动作槽；设置只表示本 tick 意图受理，原生是否派发、是否命中、是否消耗/恢复/拾取成功分别观察。没有一般性 CLI 动作命令，也没有逐帧 Python 控制。
- **一次性入口。** 正常复活由 `revive` 或 `player.revive()` 提交一次；AP 自动分配由 `auto-ap` 或 `player.auto_ap(...)` 提交一次。二者都不代表服务端结果已完成，结果不明时先观察，不重复请求。
- **单动作槽。** 同一客户端的所有 tick 会话共享唯一 `player`，按接纳顺序后写覆盖，不提供优先级治理。外部进程不能向运行中的 Lua 注入数据或指令；需要外部控制时使用文件邮箱/新会话，且必须自己保证单一控制者。
- **无内置策略。** 客户端不提供寻路、狩猎、战斗、跟随或组队任务策略；这些由用户 tick 脚本或伴游机器人应用层实现。`shared/scripts/` 只保留随镜像固定的示例和校准探针。
- **长时运行。** `script start ... --continuous` 没有总期限；死亡不会结束会话，脚本可调用 `player.revive()`。真实断线会退出进程，没有自动重连；脚本正常结束或取消后客户端继续运行。Runtime 的会话记录不会在反复启动时自动清理，事件日志只追加，长期运行需要外部监督、日志轮转和定期正常重开。

## 观察

- **角色、场景、背包、任务。** 两端按各自原生能力提供；未知字段为 `nil` 或带 `status/error`，不把缺失当已知。怪物 HP 百分比只有 headless 有稳定来源；GUI 的对应字段保持未知。
- **同图其他玩家。** `game.scene.players` 提供同图玩家的引用、角色 ID、名字、等级、位置、速度和朝向；名字/ID 可能未知，引用只在当前场景代次有效。可以据此跟随同图玩家，但不能据此确认队伍关系、队员 HP 或队友所在地图。
- **聊天与队伍。** 当前 `game.chat` 两端为 `unsupported`，没有消息读取/发送；也没有队伍成员、队员 HP、队友地图领域。玩家私聊指令、机器人回复、组队观察和入队需要新增原生能力。
- **交互。** `game.dialog/shop/ui/interaction/notifications` 按端提供只读观察；GUI 的对话、商店、背包换装、通知响应由 CLI/GUI 原生路径执行，活动 Lua 期间普通 GUI 输入会返回 `input_busy`。headless 目前不提供这些桌面/GUI 输入入口；headless 已有的 `Interaction::Activate` 还没有公开的 CLI/tick 调用入口。
- **静态资料。** 名称、物品恢复属性、NPC 范围和地图地形来自配置的原版 IMG，经共享解析库读取；静态资料辅助查询和规划，现场对象与结果仍以本端观察为准。

## 导航与跨图

- **同图导航数据。** `context.scene.terrain.navigation` 提供平台、墙、绳和几何候选关系；边代价、筛选、最短路和执行由脚本维护。客户端不内置 A*、跟随或跨平台执行器。
- **跨图路线。** `world-map route START GOAL` 是只读 CLI 查询；普通 `script run/start` **当前没有把路线注入 `context.route`**，运行中的 Lua 也不能查询路线。换图后会话保留、旧输入清除、新图地形按新场景代次重新读取，但跨图重规划需要调用方另行注入或新增运行时路线能力。
- **已知限制。** 台阶、绳梯、落下、移动平台、游泳/飞行等运动分支在两端仍有覆盖差异；复杂地图的导航应以真实客户端结果为准，不能只靠离线几何或单端通过。

## 养成与维护

- **AP。** `auto-ap`/`player.auto_ap` 按原生自动分配规则处理全部剩余 AP；不提供手动逐点 AP 分配。自动分配规则不一定等于角色的手动养成计划，使用前核对结果。
- **SP。** `skill-up` 逐点分配并核对技能等级/剩余 SP，要求当前没有活动脚本；无头与 GUI 各自有范围限制，当前目标是冒险家职业群及指定的初学者技能。
- **装备、商店、部分对话。** 由 GUI CLI 或原生 GUI 路径提供；headless 不支持。活动 Lua 期间这些操作会被 `input_busy` 挡住，因此养成必须在“停手 → 释放控制 → 维护操作 → 重新启动”的维护窗口中完成。
- **不可逆操作。** 转职、洗点、大额交易、奖励领取等需要明确计划和人工确认；客户端只提供动作与事实，不替操作者做不可逆决定。

## 能力建设优先级

伴游机器人要完成“跟随、组队、组队任务、BOSS、可选大模型”，当前最需要补的客户端能力如下。详细契约、阶段和验收见 [伴游机器人设计与路线](COMPANION_BOT.md)。

| 能力 | 当前状态 | 用途 | 优先级 |
| --- | --- | --- | --- |
| 私聊/队伍聊天收发 | 缺失 | 玩家指令、机器人回复、自然语言入口 | P0 |
| 队伍邀请/接受与成员观察 | 缺失 | 组队、跟随、队员状态 | P0 |
| headless 对象交互（NPC/对话/商店） | 原生模型已有，公开入口缺失 | 组队任务、任务、补给 | P1 |
| 运行时路线查询/注入 | 缺失 | 跨图跟随、自主旅行 | P2 |
| 玩家交易 | 缺失 | 部分经典组队任务的通行证转移 | P2 |
| 手动 AP 分配 | 缺失 | 按计划养成 | P3 |

这些条目是能力缺口，不是已交付承诺；交付时按客户端真实结果和对应验收更新本页。
