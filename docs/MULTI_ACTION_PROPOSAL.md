# tick 多动作并发：设计提案（待批准）

> **设计草案，不代表已实现。** 基线 `b75a674`；仅依据静态源码，未在 GUI 验证组合。实现须经维护者批准，不能按本文件更改当前公开契约。关联 #451、#435、#439、#325。

## 目标和现状

使同一 tick 会话能同时保持攻击或技能、跳跃、拾取、道具等独立意图，同时保留方向。意图同时存在不保证游戏同时执行，技能、动画锁、目标和服务端结果仍由原生裁决。方向+拾取已经是独立通道，不依赖本方案。

现有流程：

```text
Lua player.move ─→ 方向草稿 ─────────────────┐
Lua attack/jump/pickup/skill/use_item ─→ 单动作草稿（同 tick 后写覆盖）
                                       ↓
             TickRuntime 汇总会话草稿 → Commit → TickAdapter
                                       ↓
             GUI NativeTickInput：movement + 单 action → 原生键并集 / 技能或道具入口
                                       ↓
             原生准入与动作 → 状态观察；结束时只释放会话仍拥有的输入并等待释放确认
```

事实来源：`docs/LUA_TICK_API.md` 角色状态机；`shared/lua-runtime/TickRuntime.cpp` 的 `PlayerMove`、动作绑定、`Commit` 与会话结束路径；`shared/lua-runtime/TickRuntime.h` 的 `TickAdapter`；`beidou-ijl15/ezorsia/NativeTickInput.h`、`NativeKeyUnion.h` 和 `AgentBridge.cpp`。跳、拾取、普攻分别通过原生动作绑定 53、50、52 解析按键，不是固定键；技能和道具调用独立原生入口，不等同物理键。移动与动作按键已有 OR 合并；放键发送失败会重试，释放完成不等待动画结束。静态实现不证明任意组合在游戏内生效。

## 推荐候选 API 与兼容边界

保留现有全部 `player.*` 方法及单槽语义，包括 `skill(nil)` 清整个**旧槽**、`stop()` 清方向与所有输入。新增显式多槽命名空间（名称待批准），例如：

```lua
player.inputs.set("attack", true)
player.inputs.set("jump", true)
player.inputs.set("item", 2000000)
player.inputs.clear("jump")
-- 必须在下一 tick 或短延迟撤下 item；不能假设一次按下只消耗一瓶。
player.inputs.clear("item")
```

候选固定槽：`attack`（普攻或一个技能 ID，互斥）、`jump`、`pickup`、`item`（一个道具 ID），方向继续独立；不支持任意键或任意技能数量。`revive`、`auto_ap` 仍是独立一次性请求，不混入持键集合。候选设计中旧槽和新槽在同一会话**禁止混用**，显式失败 `input_mode_conflict`，避免旧 `skill(nil)` 意外清除并发输入；跨会话混用的全局优先级及模式切换需要维护者裁决，不能静默改变旧脚本。错误类型/不支持遵循现有 API，完整签名、版本及状态结构批准后再写入正式契约。

每槽草稿与 committed intent 各带 owner；同槽按会话接纳顺序后写覆盖，重复相同值幂等，跨槽不互相撤下；单槽 clear 仅清指定槽，所有会话共享输入，不承诺优先级。会话结束只撤销其仍拥有槽并等待该槽释放 fence；对真实虚拟键计算所有生产者引用并集，直至最后一方撤销才 keyup。`stop` 的跨会话影响需与现有共享 player 清理语义一致，并测试旧会话结束不释放后来者持有的键。物品消耗需单独节流和撤下，异常或取消不得继续消费。

状态应同时区分每槽意图、原生派发反馈和实际动作；`held` 是语义意图集合，不冒充 `held_keys` 的真实键状态。保留既有 `input_action` 投影须定义多槽歧义（建议仅旧模式提供，多槽显示未知），禁止随意挑一个伪造唯一动作。适配器如无法为各槽确认释放，应保持 `control_released=false`，不能提前宣告；输入意图受理、原生派发、角色动作和实际命中/消耗分别确认。

## 层次和实施边界

1. Runtime：将动作草稿、提交状态、owner、fence、回滚快照及错误结果按槽拆分；保留超时 `abort_commit`、跨会话调用顺序及场景切换清理。当前 `TickAdapter::SetActionIntent/ReleaseAction/ActiveAction/ActionIntentSettled` 均单值，单改容器不足以支持并发。
2. 桥：扩展接口及 `NativeTickInput`，多生产者按虚拟键并集派发并追踪独立释放；技能/道具的原生调用和动作锁门控需独立设计，不能将直接调用当键。键映射冲突、重复节奏、原生动作锁、失败补偿与多槽同步提交顺序必须实测；不要自行构造技能 keyup。
3. Lua 与 status：仅在方案批准后新增接口和公开文档；为每槽提供可判定的意图、支持状态与释放信息，并维护现有脚本兼容。跨会话竞争、单槽失败与其他槽提交、角色失效/切图需有明确规则，不假称多键原生提交原子。
4. bot：审查 `combat` 持续攻击、`loot` 拾取、`sustain` 药品及 `move` 的 jump 和 `skill(nil)` 清槽所有权；迁移须分批测试，旧 API 下方向+拾取可先独立完成。本设计不改 bot。
5. 性能：固定少量槽位和增量键状态，禁止每 tick 同步文件 IO；测量 p95/p99、最长 resume 和 overrun，#423 尚未定位，不提高预算或把并发开关当性能修复。

## 最小实施与验收矩阵

先取得批准与隔离 dev GUI 角色；离线用假 adapter 验证多槽保持、幂等、覆盖、单槽撤销、旧槽兼容、模式冲突、多个会话争用与取消、key union 同键、keyup 失败重试、fence、异常/超时回滚、地图切换及能力不支持。再构建 Windows bridge 和 GUI 镜像，验证与实际加载工件一致。动作结果分别核对意图、派发、真实 held keys、角色状态和游戏效果，不把 API `true` 当成功。

| GUI 场景 | 当前设计状态 | 最小可观察结果 |
| --- | --- | --- |
| 移动+攻击 | 未实测 | 两通道分别保持，方向改变及攻击受理/效果独立核对 |
| 跳+攻击 | 未实测 | 两个意图并存，逐项观察起跳、攻击与放键 |
| 移动+拾取 | 现有架构可同时提交，实际效果需验证 | 边移动边拾取、背包变化及键释放 |
| 跳+拾取 | 未实测 | 起跳、拾取、独立撤销与实际背包变化 |
| 攻击+拾取 | 未实测 | 同时意图及原生动作准入/效果；被拒绝须明确 |
| 喝药+移动/攻击 | 未实测 | HP/库存变化、一次撤下、不重复消耗 |
| 替换/取消/切图/两个会话 | 未实测 | 所有权、物理 keyup、control_released，后继所有者不受损 |

组合无法生效时记客户端实际拒绝/未知；不得以键已发送替代游戏效果。验收需在 dev 记录角色、镜像与桥版本、场景、每组合至少正/撤销/失败情形及原始证据，未经验收不宣称支持。现有 `docs/business-map/field-play.yaml` 描述单槽事实；本 PR 只是提案，实施被批准时须在同一分支同步业务流程、正式契约和实现。
