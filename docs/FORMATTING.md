# 格式与文件组织

自维护代码沿用现有主流写法：Python、C++、Lua 使用四空格缩进，源码使用 UTF-8、LF 和文件末尾换行。格式工具只处理明确白名单，文件职责和有意义的段落划分由评审核对。

## 检查与写入

工具版本集中在 [format_versions.json](../tools/format_versions.json)，使用 Ruff format、clang-format 和 StyLua；它们只用于开发检查，不加入客户端运行依赖。准备 Python 与 Node/npm，按[格式工作流](../.github/workflows/format.yml)从同一清单通过 pip 安装前两项、通过官方 npm 包 `@johnnymorganz/stylua-bin` 安装 StyLua 后，从仓库根运行同一个入口：

本地先建立独立开发虚拟环境，将它的 `bin` 和 npm 安装目录的 `node_modules/.bin` 加入 `PATH`。项目内临时安装放在主检出的 `tmp/<任务标识>/`，安装命令与版本读取方式复用工作流中的安装段。此检查入口用于完整 Git 检出，开发环境安装格式工具即可。

```bash
python3 tools/format.py --check
python3 tools/format.py --write
```

入口先核对已安装的工具版本，缺少工具或版本不匹配时直接报错。`--check` 检查并返回失败状态，`--write` 应用排版。两者使用相同白名单和配置；写入后再检查，重复写入保持输出稳定。CI 使用同一检查入口记录结果，不新增远端强制合并门禁。

[ruff.toml](../ruff.toml)、[.clang-format](../.clang-format) 和 [stylua.toml](../stylua.toml) 分别定义各语言的具体排版，行宽以配置为准。[.editorconfig](../.editorconfig) 补充编辑器的基本格式约定，格式检查以格式入口为准。变更规则时先检查代表文件的差异，再整理白名单。

## 排版规则

Python：

- 导入区与模块常量区之间允许一至两空行，沿用当前模块留白；顶层函数、类定义之间留两空行，类方法之间留一空行。函数内部只在逻辑段落之间留一空行，连续空行最多一行；顶层连续空行最多两行。
- 函数调用名与左括号之间不留空格；关键字与条件之间、逗号后、赋值及二元运算符两侧的空格由 Ruff 统一。括号内首尾不额外加空格。
- 超出行宽的参数列表、集合和表达式由 Ruff 分行；多行内容使用一层续行缩进。排版只处理格式，导入顺序与 lint 修复各自独立处理。

C++：

- 使用四空格和同行左花括号。独立类型、函数及类方法定义之间留一空行，短 getter 定义也遵循这一规则；同一组纯声明可连续排列。类的首个访问标签紧接左花括号，后续访问标签前留一空行。函数内部逻辑段落之间留一空行，连续空行最多一行。
- 控制语句关键字与左括号之间留一空格，函数调用名与左括号之间不留空格；逗号后及二元运算符两侧留空格。指针、引用、初始化列表和长条件的具体排版以 clang-format 配置为准。
- 参数列表和表达式超出配置行宽时交给工具续行，续行的非赋值二元运算符放在新行开头。首批保留 include 原有分组、顺序和既有注释，避免移动预编译头或改变平台宏的可见性。

Lua：

- 使用四空格；简短的单语句条件和函数允许收为单行，复杂块、长参数列表和长条件按 StyLua 配置换行，关键字、逗号和运算符的空格由工具统一。
- 顶层定义、连续操作阶段之间留一空行，块开始和结束处保持紧凑，连续空行最多一行。StyLua 负责归并连续空行，语义段落划分仍需评审核对；入口同时启用其 AST 验证。
- 格式整理只调整排版，阈值、等待时间、动作顺序和现有脚手架策略保持不变。

## 文件职责与合理例外

C++ 默认在 `.h` 放接口声明与类型定义，在 `.cpp` 放普通非模板实现。模板定义、必要的 `inline`、短类内方法，以及与模板紧密相关的小型内部核心可以保留在头文件；`NativeItemUse` 和 `NativeKeyInput` 按这一例外审查，文件归属以职责为准。移动实现时仍须保持链接、ABI 和公共接口。

Python、Lua 按现有模块职责组织。harness 的 CLI、Controller、协议传输和客户端适配已经分工，共享 Runtime 的私有实现也有明确所有者；模块按职责拆分，单次使用的辅助函数保留在调用处。

白名单以 [format.py](../tools/format.py) 为唯一来源。本批覆盖格式入口自身、近期 harness、任务管理、共享 Runtime、无头适配接线、GUI 原生输入/物品核心及直接合同；Lua 仅覆盖列入白名单的示例。未列入的历史 CLI、策略脚手架和上游改造文件保留周边惯例。

装备接线整合只额外纳入实际触及的 `cli.py`、`control_scripts.py` 和 `test_unified_control.py`，不因此扩大到其余历史 CLI 文件。

第三方原始源码、生成文件、Docker 安装文件、Shell 和 Makefile 不在本批自动整理范围。Shell 按模块保留周边写法：GUI 脚本的块缩进为两空格，harness 入口的块缩进为四空格，续行沿用各自现有形式；Makefile 命令行保留语法必需的 Tab。此范围外的文件按各自周边惯例维护。

`beidou-ijl15/` 的历史 Windows 项目保留现有 GBK、带 BOM 的 UTF-8、UTF-16LE 及混合换行事实；`.editorconfig` 对该目录单独设置通用字符集、LF、末尾换行和行尾空白，保存时保持历史文件原样。新自维护源码通常使用 UTF-8；参与既有 GUI 构建且含中文的新文件按[原构建约定](../beidou-ijl15/tools/build-agent-bridge.ps1)保存为带 BOM 的 UTF-8。格式白名单与编码例外独立，历史编码和 MSVC 编译编码按现状保留。

## 整理与验证

机械排版与文件移动分别提交，保持算法、控制流程、业务语义和公开接口不变。核对差异和字面量，复用 Python AST 等证据，并执行受影响的既有合同、构建与 CI；业务行为以合同和运行结果为准。

保持行为的排版按实际组件复用已有有效运行证据，模型、游戏和练级按需启动。若发现实际语义变化，退出本格式批次单独处理。
